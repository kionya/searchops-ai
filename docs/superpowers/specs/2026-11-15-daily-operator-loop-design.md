## 1. 왜 (사용자의 말과 실측)

사용자(원장님)는 1년 전 만든 SearchOps 를 "열었다가 뭘 하면 되지? 하고 닫는다". 실측(2026-11-15, 읽기 전용):

- 열린 WorkOrder **57건** 중 대부분이 2026-08-21 생성된 옛 주소(`/web/sub/*`) 대상 "H1 추가"·"alt 추가". 최신 크롤의 실제 SeoIssue 는 **4건**.
  → 이슈가 다시 관측되지 않아도 닫히는 경로가 없다(`packages/db/src/crawl.ts` 는 upsert 만 한다).
- 홈페이지를 **2026-11-14 리뉴얼 오픈**. 옛 주소는 폐기. 옛 주소 90개 점검 결과 55개 301→200, **32개 404**(4주 노출+방문 합 ≈1,950, 대부분 옛 블로그 `/web/blog/view?id=` 저번호 글). 구글 노출 상위 페이지 거의 전부가 옛 주소다.
- 사용자의 목표(예약 문의·네이버·구글)를 **측정하지 않는다**: GA4 `conversions`(17,867) > `sessions`(4,949) — 실제 문의가 아닌 이벤트가 전환으로 잡혀 있다. 네이버 노출 데이터 0.
- 구글은 기회가 보인다(4주, 한국): 골반 필러 노출 479·3.8위·클릭 4, 어깨필러 218·7.5위·0, 겨드랑이 착색 235·4.5위·0.
- `/ebook` noindex 는 **의료법 때문에 의도적**이다(사용자 확인). 할 일로 만들지 않는다.

## 2. 누구를 위한 무엇인가

- **사용자 1명**: 원장님. 외주·직원 없음. 홈페이지 수정은 **AI(Claude·ChatGPT)에게 "이 부분 고쳐 줘"라고 시켜서** 한다(2026-11-15 확인). 관리자 화면을 손으로 고치는 방식이 아니다.
- **보는 상황**: 이동 중 휴대폰(가장 많음) + 매일 아침 출근 후 PC(실제 수정 작업).
- **수단**: 매일 아침 **텔레그램 요약**이 먼저 오고, 링크를 눌러 휴대폰용 한 장짜리 화면으로 들어간다.
- **SearchOps 의 역할**: "무엇을 고쳐야 하는지 정하고, **AI 에게 그대로 붙여넣을 지시문**까지 만들어 주는 개인 SEO 조수".

## 4. 제약

- 실행 환경: **GitHub Actions 배치만**(`batch-crawl.yml` 매일 03:00 KST, 실제로는 수 시간 밀림). BullMQ 워커는 없다.
- 웹(Vercel)은 **직접 DB 모드**. 새로 읽는 테이블마다 `scripts/sql/web-role.sql` GRANT 추가 + 사용자가 SQL Editor 에서 실행(`docs/WEB_DIRECT_DB.md`).
  웹이 **쓰기**(했어요 버튼, 주간 입력)를 하려면 해당 테이블에 `insert/update` GRANT 가 필요하다 — 최소 컬럼만.
- 시각은 전부 KST 표기(`apps/web/src/data-freshness.ts` 의 `formatKstDateTime` 재사용).
- 새 secret(텔레그램·네이버 API 등) 값은 **사용자가 직접** `gh secret set` 으로 넣는다. 코드·대화에 값 금지.
- 판정은 결정적. LLM 은 초안 문구에만, 그리고 초안은 `packages/compliance` 플래그를 거친다.

## 6. 단계별 설계

### 단계 0 — 리뉴얼 이전 지키기 (이번 주)

1. **옛 주소 점검 자동화**: 배치에 단계 추가. 대상 = 최근 90일 GSC `page` + GA4 `pagePath` 에 나온 주소 중 현재 크롤 URL 집합에 없는 것.
   각 주소를 HEAD(필요 시 GET)로 요청해 최종 상태를 본다. **404/5xx 이거나 리다이렉트 최종이 200 이 아니면** WorkOrder 1건(소스: 리다이렉트 점검, p0, 노출+방문 합으로 정렬) — 단 **같은 원인의 주소를 묶어 1건**(예: "옛 블로그 글 24개 404")으로 만들고 본문에 표로 나열한다.
   다음 점검에서 전부 301→200 이 되면 자동 완료.
   - **깊은 주소가 홈(`/`)으로만 넘어가는 301 은 정상이 아니라 "확인 필요"(p2)** 로 본다 — 구글은 이를 soft 404 로 취급할 수 있다. 2026-11-15 실측에서 55개 301 중 홈으로 가는 것은 0개. *(설계자 판단)*
   - 비교 기준 URL 은 `https://www.gowoonmom.co.kr` 정규화(apex/www, 쿼리 `id` 보존).
   - 요청은 크롤러와 같은 UA·testcookie 해제 경로(`packages/crawler-core/src/fetch.ts`)를 쓴다.
2. **일회성 체크리스트 할 일**(사람이 해야 하는 일, 자동 확인 없음 → "했어요" 누르면 완료): 네이버 서치어드바이저·구글 서치콘솔에 새 사이트맵 제출, 옛 404 복구.
3. 이미 만든 점검 결과 CSV 는 사용자에게 전달됨(스크래치패드). 코드 산출물 아님.

### 단계 1 — 매일 아침 텔레그램 + 오늘의 할 일 10개

**1a. 낡은 할 일 정리 (먼저)**
- 크롤 후처리에서: 최신 성공 크롤이 **해당 URL 을 실제로 수집했고** 같은 규칙이 다시 안 걸렸으면 SeoIssue → `resolved`, 연결 WorkOrder → `done`(감사 이벤트 남김).
- URL 이 최신 크롤에 없고 단계 0 점검에서 301/404 로 확인되면 → `obsolete`(사유: 주소 폐기)로 닫는다. 수집 한도(25쪽) 때문에 **안 읽은 페이지를 해결로 간주하지 않는다**.
- 기존 57건은 같은 로직을 1회 실행해 정리한다(마이그레이션이 아니라 배치 첫 실행에서 자연 정리).
- `/ebook` 의 noindex 처럼 사용자가 의도한 것은 "의도함" 표시로 닫고 다시 만들지 않는다(사이트별 무시 목록: `ruleId + url`).

**1b. 할 일 순위**
- 열린 WorkOrder 중 최대 10개. 정렬 키(결정적): ① 손실형(404·noindex·크롤 차단 등 "안 하면 잃는 것") ② 우선순위 p0→p3 ③ 해당 URL 의 최근 4주 노출+방문 ④ 예상 소요(짧은 것 먼저).
- 각 항목에 **AI 지시문**(복사 버튼 하나): 그 자체로 완결된 한국어 지시 — 대상 페이지 URL, 지금 상태(증거), 바꿀 내용(가능하면 정확한 값), 바꾸면 안 되는 것(의료법 문구·`/ebook` noindex 등), 끝난 뒤 확인 방법. 어떤 AI·어떤 작업 환경에 붙여넣어도 통해야 한다(사이트 소스 위치를 가정하지 않음). 규칙(ruleId)별 템플릿으로 만든다(`packages/workorders` 기존 템플릿 확장). *(형식은 설계자 판단)*
- `obsolete` 는 `WorkOrderStatusSchema` 에 없다 → 새 상태를 늘리지 않고 `done` + 종료 사유(감사 이벤트)로 표현한다. *(설계자 판단)*
- **했어요** 버튼: WorkOrder → `in_review`(웹 역할에 `WorkOrder(status, updatedAt)` UPDATE GRANT 는 이미 있다). 다음 크롤에서 확인되면 `done`, 아니면 `open` 으로 되돌리고 "다시 확인 필요" 표시. 자동 확인이 불가능한 체크리스트형은 `done` 으로 바로.

**1c. 휴대폰용 한 장 화면**
- 새 경로 `apps/web/app/sites/[siteId]/today`(기존 대시보드는 "자세히 보기"로 남김). 로그인은 기존 Supabase 세션.
- 위→아래 한 번 스크롤: 어제 대비 변화 한 줄 → 핵심 숫자(단계 2 이후 문의, 노출·클릭) → 할 일 10개(휴대폰은 제목만, 탭하면 펼침) → 데이터 반영 현황(기존 `DataFreshnessPanel` 재사용).
- 폭 360px 기준 가로 스크롤 없음.

**1d. 텔레그램 요약**
- 배치 마지막 단계에서 발송(새 스크립트 `apps/worker/src/batch-digest.ts`). 기존 봇 `SEARCHOPS_TELEGRAM_BOT_TOKEN` 재사용(`packages/connectors/src/telegram.ts`). 받는 채팅은 새 변수 `SEARCHOPS_TELEGRAM_OWNER_CHAT_ID`(원장님 1:1) — 기존 PRODUCT/OPS 채팅과 섞지 않는다. 없으면 건너뛴다(0 종료).
- 기존 `batch-geo` 주간 요약은 그대로 둔다(합치기는 별도 판단).
- 내용(휴대폰 한 화면): 경고(있을 때만, 맨 위) / 어제 대비 변화 1~3줄 / 숫자 / 남은 할 일 수 + 1순위 제목 / `today` 링크.
- **KST 07:00 이전이면 무음 발송**(`disable_notification`) — 새벽 알림 금지. *(설계자 판단)*
- 같은 경고는 상태가 바뀔 때만 다시 알린다(반복 알림 금지).
- 배치 실패 시에도 "어제 배치 실패" 한 줄을 보낸다(기존 GitHub 이슈 알림은 유지).

### 단계 2 — 예약 문의 세기

| 경로 | 매일 자동 | 실건수 |
|---|---|---|
| 카카오톡 채널 | 홈페이지 → `pf.kakao.com` 등 바깥 링크 클릭 | 드라이브 정리 파일에서 날짜별 건수 자동 집계 |
| 네이버 예약 | 홈페이지 → `booking.naver.com` 클릭 | 주 1회 텔레그램 입력 |
| 전화 | 홈페이지 `tel:` 클릭 (추적 코드 추가 필요) | 주 1회 텔레그램 입력 |

- GA4 커넥터에 `eventName` + `linkUrl`(바깥 링크 클릭, 향상된 측정) 집계를 추가한다. `tel:` 은 향상된 측정에 안 잡히므로 단계 2 첫 할 일로 "전화 버튼 클릭 추적 추가" AI 지시문(스니펫 포함)을 만든다. ⚠️ 새 사이트에 GA4 가 실제로 설치·향상된 측정 켜짐인지 첫 태스크에서 실측.
- 기존 `conversions` 는 "문의"로 표시하지 않는다(의미 불명).
- GSC·GA4 커넥터는 동기화마다 **지난 28일 합계**만 저장한다(일별 없음). "어제 대비"는 동기화 스냅샷 간 비교로 하고, 단계 0 의 90일 주소 목록은 저장된 스냅샷들의 합집합 + 필요 시 GSC 추가 조회로 만든다. *(빌더 재량)*
- 드라이브 파일: 구글 시트 API 읽기 전용. 인증은 기존 Google OAuth 자격증명에 `spreadsheets.readonly`(또는 `drive.readonly`) 범위 추가 → 사용자 재동의 1회. ⚠️ 파일 형식은 아직 미확인(아래 8절).
  환자 이름·연락처는 **읽어도 저장하지 않는다** — 날짜·건수만 저장.
  ⚠️ 운영 DB 의 `ConnectorOAuthCredential` 에 고운몸 행이 없다(2026-11-15) — GA4/GSC 가 어떤 인증 경로로 붙는지 단계 2 착수 시 먼저 확인하고, 그 계정에 드라이브 뷰어 공유가 되어 있는지 맞춘다. OAuth 앱이 Testing 상태면 refresh token 7일 만료에 주의.
- 주 1회 입력: 매주 월요일 텔레그램 요약에 "지난주 네이버 예약·전화 건수를 넣어 주세요" + `today` 화면의 **입력 칸 2개**(예약, 전화) 링크. 텔레그램 답장 파싱(`getUpdates`)은 쓰지 않는다 — 기존 봇을 재사용하므로 다른 소비자·웹훅과 업데이트를 다툴 위험이 있다. 입력이 없으면 다음 요약에서 다시 묻는다. *(설계자 판단)*
- 저장: 새 테이블(예: `InquiryCount`: siteId, 기간 시작·끝, 채널 kakao|naver_booking|phone, 출처 site_click|drive|manual, 건수). 마이그레이션 + web GRANT(manual 행 insert/update 포함).

### 단계 3 — 구글: 순위는 높은데 클릭이 없는 검색어

- GSC 기록에서 결정적으로 고른다: 평균 순위 ≤ 10, 4주 노출 ≥ 100(초기값, 조정 가능), CTR 이 같은 순위대 기대치보다 현저히 낮음.
- 할 일 = 해당 페이지의 **검색 결과 제목·설명 고치기**. 초안 문구 2안은 v1 에서 **결정적 템플릿**(검색어·시술명·지역·병원명 조합)으로 만든다 — batch-crawl 에 LLM 키가 없고 Gemini 무료 한도(하루 20건)가 이미 GEO 에 쓰인다. LLM 초안은 템플릿 품질이 부족할 때 별도 태스크. *(설계자 판단)* + `packages/compliance` 플래그. 등급 처리(결정 11): critical·high → 복사 차단 + 사유, medium·low → 경고 문구와 함께 복사 허용. 화면에 "검사 통과는 법적 승인이 아니며 게시 판단은 원장님" 고정 문구. 같은 규칙을 단계 1 AI 지시문 속 환자 대상 문구에도 적용.
- 효과 확인: 4주 뒤 같은 검색어 CTR 비교를 할 일 완료 기록에 붙인다.

### 단계 4 — 네이버 네 영역

- 네이버 공식 **검색 API**(developers.naver.com — 웹문서·블로그·카페글·지역). 키워드 = 기존 `Keyword`(purpose `search_demand`/`both`) 중 월간 검색량 상위 N. 매일 1회.
  - 사이트: 웹문서 결과에서 `gowoonmom.co.kr` 순위.
  - 블로그: 고운몸 블로그 글 순위.
  - 카페: 고운몸 언급 글 수(추적만).
  - 플레이스: 지역 검색 상위 5 안 순위, 밖이면 "5위 밖". ⚠️ API 결과 순서 ≠ 실제 화면 순서일 수 있음 — 화면에 그 사실을 표기.
- 블로그 주제 추천: GSC·네이버 검색량에서 "찾는 사람은 많은데 우리 글이 약한 주제" → 기존 `ContentBrief`(draft-only) 로 연결.
- 플레이스 관리: 자동 확인 불가 → 주기적 체크리스트 할 일(사진·소식·리뷰 답글).
- secret: `SEARCHOPS_NAVER_SEARCH_CLIENT_ID`, `SEARCHOPS_NAVER_SEARCH_CLIENT_SECRET`(기존 검색광고 키와 별개, 사용자가 앱 등록).

## 7. 성공 판단

- 사용자가 텔레그램 링크로 들어가 **할 일을 실제로 완료**한다(했어요 클릭이 주 1회 이상).
- 열린 할 일이 10개 안팎으로 유지되고, 낡은 항목이 남지 않는다.
- 옛 주소 404 가 0 이 된다.
- 단계 2 이후 주간 문의 건수(3경로)와 네이버·구글 노출 추이가 한 화면·한 메시지에 나온다.
